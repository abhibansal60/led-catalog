# .led file format research — gist & Windows starter

Working notes on reverse-engineering the T1000/T8000 `.led` program format, so a
future session (or a session on the Windows machine) can pick this up without
re-deriving context. Not an ADR — this is research-in-progress, not a settled
architecture decision.

## The original problem

Bansal Lights installs temporary LED light shows on buildings, driven by
T1000/T8000 SD-card pixel controllers. Updating or fixing a show means
physically climbing to the controller, swapping the SD card, and hoping the
copy worked — often discovered wrong only after climbing back up. That pain
is largely solved now (see "Shipped" below). The remaining open question is
whether we can *preview* what a `.led` file will actually display before it
ever reaches a card, which requires cracking the file format.

## Shipped (this repo, already live)

- `src/lib/ledFile.ts` — header sanity check (magic bytes, sync marker,
  LED-count field) + SHA-256 file hashing/comparison.
- `src/lib/clearDirectoryContents.ts` — wipes the SD card folder before copy.
- App.tsx: copy-to-SD now verifies byte-for-byte after writing; a standalone
  "Verify SD Card" button re-checks anytime; add-time integrity check rejects
  corrupted files before they enter the catalog.
- CI now stamps the real build date/commit into the footer version
  (`.github/workflows/deploy.yaml`).

These four features address the *actual* stated pain (repeat trips from bad
copies) without needing the file format cracked at all.

## Format findings so far

Confirmed by diffing header bytes across two real field files
(`test-files/00_program_25x40_zameer_parallel.led` = 25×40 = 1000 pixels,
`test-files/50x40 koshi/00_program.led` = 50×40 = 2000 pixels):

| Offset (bytes) | Field | Notes |
|---|---|---|
| 0-6 | `rzbv001` magic | ASCII, constant across all known files |
| 14-15 | `32 20` | constant marker |
| 20-23 | `00 55 aa 00` | constant sync marker |
| 37-38 | LED pixel count | big-endian uint16, confirmed 1000 and 2000 |

Everything past the ~64-byte header is either encrypted, compressed, or a
palette/RLE-coded animation stream — no public spec exists (checked web
search, nothing). Byte patterns don't decode cleanly under any format
guessed so far. **Cracking this needs known-simple test files** (solid
color, single pixel, 2-frame blink) generated by the real LedEdit software
and diffed byte-for-byte against each other.

## Why this moved to Windows

Tried running LedEdit 2014 under Wine on this Ubuntu box to generate test
patterns. Hit a real chain of Wine-specific compatibility issues in order:

1. Wine Mono missing → needed real .NET via winetricks.
2. `dotnet48` pulled in `dotnet40` as a dependency (flaky under Wine per
   winetricks' own warning).
3. LedEdit's `.exe.config` actually requires **.NET v2.0.50727** specifically
   (not 4.x) — needed `dotnet20sp2` too.
4. Menus rendered as `□□□` tofu boxes (LedEdit's UI is Chinese) — needed
   `winetricks fakechinese` to install font aliases.
5. LedEdit finally ran, but `.led` files can't be opened in it — turns out
   `.led` is a one-way *export* format; LedEdit only opens its own `.pxb`
   project files.
6. Tried LEDPlayer 2024 (a lighter playback-only tool) instead — installed,
   but crashed natively (likely missing VC++ redistributable).

Every blocker was a Wine translation-layer issue, not a real problem with the
task. Concluded it's faster and more reliable to just do this on a real
Windows machine. **Wine and all related files have been removed from this
Ubuntu machine** (`~/.wine`, `~/.local/share/ledit`, the `ledit` bash alias,
and the `wine`/`winetricks` apt packages).

## Starter: continuing on Windows

1. Run `setup-ledit-windows.ps1` (in this same `docs/` folder) as
   Administrator — it enables .NET Framework 3.5, installs the VC++
   redistributable, and downloads+extracts LedEdit 2014 and LEDPlayer 2024
   to `Desktop\LedEdit-Tools`.
2. Open LedEdit, set controller = **T1000** (or whatever the real controller
   model is), smallest pixel count available.
3. Create these small test effects and export each via 工程输出 (Project
   Output) as `.led`, with clear filenames:
   - All pixels solid red, 1 frame
   - All pixels solid green, 1 frame
   - Only the first pixel white, rest off, 1 frame
   - (bonus) 2-frame red→black blink
4. Send the resulting `.led` files back, along with the exact settings used
   (pixel count, controller model, frame rate) — diff them byte-for-byte
   against each other and against the real field files in `test-files/` to
   crack the color/frame encoding.
5. Once cracked, the payoff is a real in-browser preview/simulator added to
   this catalog app — render the decoded frames on a `<canvas>` grid matching
   the physical layout, so a program can be checked before it ever reaches an
   SD card.

## Hardware alternatives considered (rejected)

Explored replacing physical SD-card handling with remote/wireless feeding:

- **WiFi SD cards** (FlashAir-successor style): market is dead, discontinued
  or unmaintained.
- **Official T1000/T8000 network module**: doesn't exist. LedEdit's "网络联机"
  (Network Online) mode only supports a different controller family
  (T-100K/200K/300K), and requires a PC continuously connected and streaming
  at the site — live remote control, not fire-and-forget upload.
- **SD WIFI PRO** (FYSETC, ESP32-based SD-card emulator, open-source): the
  closest real product, but not available in India without importing.
- **Passive SD extension cables**: available in India, but only reliable to
  ~25-80cm — nowhere near enough to relocate a card from a rooftop
  controller to ground level.
- **DIY ESP32 SD-emulator build**: technically buildable (open-source
  firmware/PCB design exists), but a real electronics project (PCB fab,
  soldering, firmware flashing), not a quick fix.

Given the business is temporary lighting decor (short job cycles, physical
access already happens during setup/teardown), sinking cost into permanent
remote-feed hardware wasn't judged worth it. The already-shipped software
fixes (verify/format/integrity-check) were judged to solve most of the real
pain for near-zero cost. This thread is parked, not pursued further.
